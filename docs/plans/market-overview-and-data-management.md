## 模块与调用关系

浏览器经现有 Cloudflare Access／Tunnel 到达网站 Go 服务；网站服务提供两页前端和必要的业务转发，经内部鉴权调用 syncer；只有 syncer 访问 MySQL 与行情源。前端建议使用 TypeScript + Vite + ECharts，不另引入前端服务端运行时。

| 边界 | 对调用者提供 | 内部隐藏 |
| --- | --- | --- |
| 数据维护 | 数据目录与覆盖、接入、启停、提交、查进度、取消、失败重试 | 各类数据源差异、批次拆分、固定范围、分段提交、互斥、去重、中断恢复 |
| 市场总览 | 某周期的完整行情与指标、月度正式／暂算结果、可用性与截止日 | 聚合、EMA、日历规则、修订传播、一致快照与整体发布 |
| 网站访问 | 受保护的页面及上述业务操作 | Access 验证、内部密钥、转发白名单、同源写操作检查 |

沿用现有数据源适配器与 Go 测试习惯，仅在需要容纳持久执行或市场查询的地方加高层边界。两个业务边界不要求拆成两个进程；首版放在现有 syncer 内。

## 与现有实现的差距

| 当前代码证据 | 必须解决的差距 |
| --- | --- |
| [HTTP 同步逻辑](../../syncer/internal/logic/syncetfdailylogic.go) 随请求等待核心运行结束 | 提交时持久接受，后台独立执行；断开连接不等于用户取消 |
| [ETF 同步核心](../../syncer/internal/core/sync.go) 使用最新日期和默认起点 | 新指数／新 ETF 全源历史；历史重同步需自己的区间检查点，不能用表内最大日期推断完成 |
| [申万同步核心](../../syncer/internal/core/sw.go) 分字典、成员和日线 | 把现有能力纳入统一执行记录；字典和成员刷新不能伪装为日期补数 |
| [信号入口](../../syncer/internal/logic/rotationsignallogic.go) 与 [收盘日报入口](../../syncer/internal/logic/rotationclosereportlogic.go) 读取启用同步名单计算 | 同步继续覆盖所有启用对象，计算单独读取策略候选；不能只替换一个列表导致新 ETF 不再被同步 |
| [建表逻辑](../../syncer/internal/schema/schema.go) 只有幂等建表 | 增加有版本的迁移，一次性复制当前候选；重启、升级和新接入不能再次扩充候选 |
| [ADR-0001](../adr/0001-cron-triggered-stateless-syncer.md) 规定服务无状态且没有内部调度 | [ADR-0009](../adr/0009-durable-sync-execution-with-external-cron.md) 已明确修订：外部 cron 继续决定每日何时触发，syncer 新增持久执行协调和恢复 |
| [部署配置](../../deployments/compose.yaml) 已有 MySQL、syncer、机器人 | 增加网站服务，保持内部服务端口边界，不改动已经完成的用户隧道与登录配置 |

## 持久执行提案

提交前校验并规范化类别、对象代码、操作及日期。批次固定对象集合，每个子项固定自己的实际起止范围；增量请求同时保存提交时的目标截止日。相同未完成请求复用已有批次，不同范围的请求按对象排队。

MySQL 保存批次、对象子项、阶段／日期分段、错误、取消意图、执行权及恢复事件。初版默认保守地串行消费工作，仍以数据库约束和执行权校验防止进程重叠或旧入口绕过。无需新增 Redis 或消息队列。

对象的分段写入与检查点在同一事务提交。源端允许重读，依靠主键写入幂等保证不会产生重复行；不承诺网络请求恰好发生一次。ETF 日线和因子、申万字典和成员分别记录阶段，已完成阶段不因后续失败丢失。

取消意图持久化；每段写入前检查执行权与取消状态。在取消事务之前已提交的数据保留，在其之后不再提交新段。旧进程即使从阻塞的源端请求返回，也不能在失权后继续写入。重启恢复沿用原子项和范围，取消的子项不恢复。

只重试失败对象；成功对象不进入新执行范围。失败对象内复用可信检查点，只有未完成或无法确认提交的分段可以重读。批次需区分全部成功、部分失败、已取消和运行中，不能用一个总体成功标记掩盖对象失败。

历史重同步提交时就标记该对象正在维护，保留原始数据已提交部分，但不发布半套行情衍生结果。价格修订导致后续所有 EMA 受影响，初版可全历史重算，避免增量计算缓存的复杂性。

## 市场结果发布提案

计算从一致的原始数据快照读取完整历史，并携带数据修订标识；完整计算后检查标识仍有效才切换当前结果。暂存候选失败即丢弃，成功后旧结果可清理，不建立市场状态历史档案。

市场查询返回同一完整版本的价格、指标和状态输入，再结合查询时的上海时间、交易日历和维护进度附加可用性。月末已到而新数据未就绪时，旧结果只能显示真实月份，当前正式提示必须停用。未完成首次回填时显示尚无完整结果，不把早期片段当成全部历史。

源端范围要有覆盖证据：优先利用指数／ETF 元数据，并按足够小的日期窗口获取、检测截断和缺失。空响应、权限不足、限流、上市前日期必须区分；不声称本次文档检查已经验证生产账号的历史覆盖或权限。ETF 验证首选专属元数据，账号权限不足时先报告，不能凭名称含 ETF 或场内标志放行。

## 建议交付顺序

1. **统一访问入口与只读数据管理**：建立受现有 Access 保护的网站、两页导航、分类数据覆盖查询；保留研究页面和机器人入口。
2. **可恢复的数据维护闭环**：以中证全指接入贯通全历史、持久任务、进度查询、取消与恢复，再统一 ETF／申万及旧入口的执行协调。
3. **ETF 名单隔离与管理**：一次性迁移现有策略候选，接入／启停 ETF，保证新增数据不会改变现有策略。
4. **市场总览闭环**：日历、日周月聚合、MACD、正式／暂算提示、缺数与更新状态、完整结果发布和历史修订重算。
5. **自动更新与上线验收**：接入 18:00 上海时间外部 cron，检查非交易日报告兼容、权限、重启恢复、失败重试及完整用户流程。

步骤间可渐进展示成果，但最终验收包含完整 PRD，不因基础页面完成而省略恢复、取消或一致性要求。测试随每个交付步骤建立；具体工单已按用户批准的拆分发布。

## 测试约定与本次检查范围

测试集中于数据维护业务入口、市场查询入口和少量浏览器流程。现有内存数据源测试用于确定性数值／失败场景；恢复、互斥、取消竞争和整体发布使用隔离真实 MySQL 验证。避免只验证 mock 调用次数或复制实现公式作为唯一预期值。

本次只核对需求覆盖、文档间口径、现有代码边界和引用，未修改业务代码，也未运行应用测试。实际源端权限、数据覆盖、生产 Access 配置和部署可达性尚未验收。
